# 架构设计文档撰写

产出"基于现有代码库真实约束、场景驱动、含治理与降级设计"的系统架构设计文档。与 `tech-report-writing`（调研已有技术）区分：本技能面向**为业务需求设计新方案**，第一事实源是目标代码库本身，外部资料只做方法论参照。

## 触发条件

- 用户要求"设计一个 XX 系统"、"写架构设计文档"、"帮我完成 XX 的设计方案"
- 用户给出业务背景 + 指定复用某基础组件/SDK/服务
- 用户说"现有实现仅作参考/并不完整，重新设计"——意味着不要迁就旧模型，先识别旧模型与新需求的根本冲突

## 工作流（六步）

### 步骤 0：需求本质判断（最关键）
新需求可能与现有实现的核心假设**根本冲突**（如"话题硬隔离" vs "跨群知识流动"）。先一句话说清冲突点，设计立场写在文档开头：是修补旧模型还是重建模型。不要默认在旧模型上打补丁。

### 步骤 1：代码库 grounding（先于一切外部检索）
- `git log` / README 了解项目现状与惯例；
- 精读与目标系统相邻的模块源码（存储层、调度层、工具层）：数据模型、隔离键、并发模型（子进程？文件锁？）、降级行为；
- 检查依赖清单（pyproject/package.json）——用户指定的"基础组件"往往**已经装进 .venv**；
- 把代码里的真实约束变成设计约束（如"每条消息一个 spawn 子进程"→ 客户端禁止跨进程共享；"同话题文件锁串行"→ 无需服务端并发控制）。

### 步骤 2：基础组件能力盘点（SDK 源码优先）
- **内部平台文档站常需公司 SSO，浏览器到登录页就停——不要硬闯**。此时以项目 `.venv` 内已装 SDK 源码为权威事实源（client 源码 = 全量 API + 参数白名单 + 鉴权方式 + 错误类型），并在文档中如实注明"文档未能访问，以 SDK 源码为准，落地前复核"；
  - 已有速查：`references/memorybase-sdk.md`（字节 MemoryBase/mem0 SDK 全量 API + 工程约束，飞书/内部项目直接复用，落地前比对实际安装版本）；
- 盘点输出成表：方法 / 关键参数 / 用途；
- 单列"工程约束"小节：鉴权细节、客户端生命周期、同步/异步模式、错误处理、严格参数校验（升级风险）。

### 步骤 3：外部方法论检索（补理论，不补事实）
- 知乎检索（走 `zhihu` 技能）找业界同类系统的设计原则与踩坑结论，用于支撑设计决策（如多 Agent 记忆共享的"私有默认、共享显式"、检索深度与泄露正相关）；
- 检索结果只进"设计参照"与"参考资料"章节，不冒充一手依据；一手依据 = 代码库 + SDK 源码。

### 步骤 4：成文（固定骨架，输出到 `<repo>/docs/<topic>-design.md`）
1. **背景与目标**：现状痛点表（编号 + 细节），设计目标（编号、可验收）；
2. **设计参照**：逐个列出参照系统，表格映射"参照机制 → 本方案对应物"，并写明**关键差异**（为什么不能照搬）；
3. **基础组件能力盘点**：步骤 2 的表 + 工程约束；
4. **总体架构**：分层模型图 + 层间关系表（每层：scope/写入方式/可见性/内容形态/类比）+ 端到端数据流时序图；
5. **详细设计**：模块划分（文件树 + 职责一句话）、读写管道、命令层、配置项（环境变量示例）、并发模型、治理（密级/权限/审计）；
6. **场景走查**：选 1~3 个典型场景画时序图逐步推演，验证设计闭环（含负向场景：泄露/故障时行为）；
7. **实施路线图**：分阶段表（阶段/内容/交付物/验收标准），验收要可执行（含泄露回归这类负向测试）；
8. **风险与注意事项**：风险/影响/缓解三列表，第一条放最大风险；
9. **参考资料**：分"一手依据（本环境已验证）/ 方法论参考（知乎，带标题+作者+URL）"。

### 步骤 5：图表
- **全部用 Mermaid**（flowchart / sequenceDiagram），放 ```mermaid 代码块——用户明确偏好，ASCII 框图会被嫌丑且 CJK 对齐必错；
- 至少：一张分层/总体架构图 + 一张核心数据流时序图 + 场景走查时序图；
- 不需要 browser 渲染验证（Mermaid 由 GitLab/VS Code 原生渲染）。

## 常见坑

1. **把"现有实现"当设计约束**：用户说"仅作参考"时，旧实现是批判对象不是地基；先找出旧模型与新需求的冲突点并声明设计立场。
2. **隔离/共享类需求只设计一面**：跨域共享必须同时设计治理——密级分级、默认私有/显式共享、客户端侧强制校验兜底（不信任服务端单侧）、全链路溯源（出处字段随记忆/数据走，防模型编造）、审计日志、负向回归测试（泄露必须可复现验证）。
3. **忘设计降级**：外部服务不可用时回退到本地/现状行为，且"回复/主流程永不阻塞"要写成显式降级矩阵（故障×读写路径）。
4. **写入通道全同步**：异步沉淀放回复之后 + 后台轮询，幂等整合特性允许失败下轮补偿；注明不阻塞的边界。
5. **硬编码密钥**：检索/测试脚本里遗留的硬编码 API key 要在文档风险和路线图里点名清理。
6. **场景表先于架构**：第 1 章就列典型场景表（场景/知识源/消费方/期望行为），后续每个设计决策都能回指场景编号（S1..Sn）。

## 验证清单

- [ ] 文档开头写明了与旧实现的冲突点和设计立场
- [ ] 每条设计约束可追溯到代码库事实（文件/行为）
- [ ] 基础组件能力表来自 SDK 源码实读，非凭记忆
- [ ] 图全为 Mermaid；含架构图+数据流时序图+场景走查图
- [ ] 治理三件套齐备：密级/权限、溯源、审计；含负向测试验收项
- [ ] 降级矩阵覆盖外部服务故障路径
- [ ] 参考资料区分一手依据与方法论，知乎条目带 URL
