# 静态评分细则（Scoring Rubric）

静态评测不运行 Skill，只读 `SKILL.md` + `references/` + `scripts/` 元信息。
6 维评分，每维 0-5 分，总分加权后映射到 0-100。

加权：知识增量 × 1.5，其余维度 × 1.0（共 6.5 个权重，再线性映射到 100）。

> 评分一定要给出"扣分理由"和"原文片段引用"，不能只给数字。

---

## 维度 1：知识增量（Knowledge Delta，权重 ×1.5）

**核心问题：** Skill 是否提供了 LLM 不知道的专家知识？

| 分 | 描述 |
|----|------|
| 5 | 80%+ 内容是 LLM 训练数据中没有的（内部流程、专属规范、特定平台 API、领域专家经验） |
| 4 | 60-80% 是增量知识 |
| 3 | 40-60% 是增量，但有不少通用知识混杂 |
| 2 | 20-40% 是增量，大部分是 LLM 已知 |
| 1 | <20% 是增量，几乎都是通用知识 |
| 0 | 全是通用知识（Git 命令、HTTP 协议、Markdown 语法等） |

**判定方法：**
逐段检查 SKILL.md，问自己："如果我不引用外部知识，我是否已经知道这个了？"
- 是 → 标为通用知识
- 否 → 标为增量

通用知识占比 = 通用段落数 / 总段落数。

**典型反例（≤2 分）：**
- 大段介绍 Git 工作流、HTTP 状态码、SQL 语法
- 重复某些已知框架的基础概念
- "如何使用 Python 写脚本" 这类元知识

---

## 维度 2：思维模式与领域流程（Thinking Pattern & Domain Flow）

**核心问题：** 是否传递了"专家如何思考"和"领域 SOP"？

| 分 | 描述 |
|----|------|
| 5 | 完整列出领域 SOP（步骤 + 输入输出 + 决策点），有专家思考框架 |
| 4 | 主流程清晰，但部分决策点缺失 |
| 3 | 有流程描述，但偏笼统，决策点表达不清 |
| 2 | 流程零散，需要 Agent 自己拼凑 |
| 1 | 几乎没有领域流程，仅是工具说明 |
| 0 | 没有任何流程性内容 |

**重点检查项：**
- 是否给出"先做什么后做什么"的明确顺序？
- 关键决策点（"如果 X 则 Y，否则 Z"）是否写明？
- 是否列出"专家会注意的细节"（不是"建议小心"这种空话）？

---

## 维度 3：反模式知识 / Gotchas（Anti-pattern Knowledge）

**核心问题：** 是否有具体、有出处的"绝对不能做"清单？

| 分 | 描述 |
|----|------|
| 5 | ≥5 条具体 Gotcha，每条都有"为什么"或来自真实失败案例 |
| 4 | 3-4 条具体 Gotcha |
| 3 | 1-2 条具体 Gotcha + 一些泛泛而谈的注意事项 |
| 2 | 只有"注意安全"、"小心使用"这类空话 |
| 1 | 完全没有 NEVER / 边界 case 描述 |
| 0 | 反向：写了一些会误导的"建议" |

**好的 Gotcha 长这样：**
> NEVER 在评测时单独挂载这一个 Skill —— 命中率会虚高，无业务参考价值（来自 2025-XX 内部回归实测）。

**坏的 Gotcha 长这样：**
> 注意保持代码整洁。
> 小心处理边界情况。

---

## 维度 4：规范合规度（Spec Compliance，重点看 Description）

**核心问题：** `description` 是不是合格的"路由触发器"？

| 分 | 描述 |
|----|------|
| 5 | description ≤50 词；用"Load when…/适用于…"句式；明确意图、能力、典型场景 |
| 4 | 满足上述大部分，但措辞略冗 |
| 3 | description 可读，但偏向"功能说明"而非"触发条件" |
| 2 | description 是说明文档（"本 Skill 用于 / 由 X 团队定制"） |
| 1 | description 严重缺失关键意图词 |
| 0 | description 缺失或不可解析 |

**额外硬性检查（任一不通过，本维度 ≤2 分）：**
- name 是 hyphen-case，全部小写
- name 与目录名严格一致
- YAML frontmatter 仅含 `name` / `description` / `author`，无其他字段
- description 不含"本 Skill"、"由 XX 团队"等无效词

---

## 维度 5：渐进披露（Progressive Disclosure）

**核心问题：** 三层结构是否合理？

| 分 | 描述 |
|----|------|
| 5 | SKILL.md <500 行；条件分支全部外移到 references；scripts / assets / references 各司其职 |
| 4 | SKILL.md ≤500 行，绝大部分分支已外移 |
| 3 | SKILL.md 接近 500 行边界，部分分支应外移而未移 |
| 2 | SKILL.md >500 行 OR 大量分支堆在正文 |
| 1 | 几乎没有分层，全部塞在 SKILL.md |
| 0 | 结构混乱（references 里有该在 SKILL.md 的内容，反之亦然） |

**自动检查项：**
- SKILL.md 行数（用 `wc -l`）
- references 文件数量与命名规范
- SKILL.md 中是否引用了所有 references 文件（未被引用的 references 是死文件）
- 是否有 stub 脚本（仅 `pass` / `print`，无逻辑）

---

## 维度 6：自由度校准（Autonomy Calibration）

**核心问题：** 约束程度是否匹配任务的脆弱性？

| 分 | 描述 |
|----|------|
| 5 | 窄桥用脚本固化（低自由度），开阔地用文本指导（高自由度），匹配恰当 |
| 4 | 大体匹配，个别地方偏紧或偏松 |
| 3 | 一刀切（要么全脚本，要么全文本），没有按场景区分 |
| 2 | 该用脚本的地方用文本（任务脆弱却没有护栏） |
| 1 | 该用文本的地方用脚本（任务开放却被脚本锁死） |
| 0 | 自由度完全失配 |

**判定线索：**
- 涉及"格式严格输出（JSON/Schema/特定数据结构）" → 应有脚本验证
- 涉及"有标准 SOP 但需灵活措辞" → 应有伪代码 / 模板
- 涉及"开放讨论 / 写作 / 设计" → 应是文本指导，不要脚本锁死

## P0 / P1 / P2 问题分级

不是所有扣分都同等严重。报告中按下面分级：

### P0（阻塞上线，必须修复）
- `description` 缺失、不可解析或与功能严重不符
- name 与目录名不一致
- YAML frontmatter 含非法字段
- SKILL.md 文件不存在
- 脚本是 stub（仅 `pass`）但被 SKILL.md 标为"必须运行"
- SKILL.md 引用的脚本 / references 文件不存在
- 触发评测命中率 <50% 或误触率 >20%（如果跑了阶段 2）

### P1（强烈建议修复）
- 知识增量 ≤2（Skill 没价值）
- Gotchas 全是空话（≤2 分）
- SKILL.md >500 行且没有分层
- 自由度严重失配
- 跨模型触发命中率方差 >30%

### P2（优化项）
- description 措辞可优化但能用
- references 命名不统一
- 报告 / 注释中的小排版问题
- Token 消耗略超预算（<20% 超出）

## 总分到分级映射

| 总分 | 等级 | 含义 |
|------|------|------|
| 90-100 | A | 优秀，可作为模板供其他 Skill 参考 |
| 75-89 | B | 良好，有 1-2 个 P1 问题需迭代 |
| 60-74 | C | 合格，建议修复 P1 问题后再发布 |
| 40-59 | D | 不合格，需要重大修改 |
| <40 | F | 重写 |

**注意：** 即使总分 ≥75，只要存在 P0 问题，最终结论必须是"暂不通过，需先修复 P0"。
